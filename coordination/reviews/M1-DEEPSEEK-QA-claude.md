## Findings

### M1 — `createStudyProgram()` silently emits duplicate identities after the fifth call

`tests/foundation/fixtures/study-program.ts:31` indexes the program list modulo its
length: `programs[(studyProgramIdCounter - 1) % programs.length]`. The `id` is derived
from the program code, so the sixth call wraps back to IAT and returns an object with the
**same `id`, `code`, and `slug`** as the first. Reproduced:

```
test-prodi-iat (IAT)
test-prodi-ih (IH)
test-prodi-afi (AFI)
test-prodi-saa (SAA)
test-prodi-taspi (TASPI)
test-prodi-iat (IAT)   ← duplicate of call #1
```

The factory's job includes feeding the DB integration tests that verify unique
constraints. A test that seeds six programs will either hit a unique violation that looks
like a schema bug, or silently overwrite a row. The wrap is invisible at the call site.

Suggested fix: throw past the fifth program (there are exactly five prodi by contract), or
take an explicit index/code argument, plus a `createAllStudyPrograms()` helper for the
common case. Add a test asserting six calls do not collide.

### M2 — locale direction is now defined in two places, and the tests only check their own copy

`src/test/locale-helpers.ts:6` hardcodes `RTL_LOCALES = new Set(["ar"])`, while the app
decides direction independently at `src/app/[locale]/layout.tsx:39`
(`dir={locale === "ar" ? "rtl" : "ltr"}`). `locale-validation.test.ts` then asserts
`getLocaleDirection("ar") === "rtl"` — that is the helper testing its own constant, and it
would keep passing if the layout regressed. `SUPPORTED_LOCALES` is derived from
`routing.locales`; direction should be derived the same way rather than restated.

This is the same duplication class the integrator already made you fix for the program
list (v2 fix #3). The real RTL guarantee currently rests on `rtl-negative.spec.ts`, which
does assert the rendered `html[dir]` — so the app is covered; the unit layer is just not
pulling its weight.

Cleanest fix is a contract change (GPT-owned): export a single `getLocaleDirection()` from
`src/i18n/routing.ts` and have both the layout and the test helper consume it. Until that
lands, keep the helper but stop treating its assertions as RTL coverage.

Also: `LTR_LOCALES` (`locale-helpers.ts:7`) is dead — `isLtrLocale()` is defined as
`!isRtlLocale()` and never reads it. Two sources that can silently disagree.

### M3 — `e2e/foundation` is pinned to the M0 placeholder homepage and will break on contact

`locale-routing.spec.ts` asserts `getByText("FUSPI · M0")` and a visible `h1` on
`/{locale}`; `rtl-negative.spec.ts` asserts `body` contains `"FUSPI"` there. That route is
`src/app/[locale]/page.tsx`, the M0 placeholder. My M1 handoff filed a contract request for
GPT to move the homepage into `src/app/[locale]/(public)/page.tsx` so the public shell can
own it — the moment that lands, the `"FUSPI · M0"` assertion fails and the h1 assertion
becomes coincidental.

These are foundation tests, so they should assert structural invariants that survive the
real homepage (`lang`/`dir`, a level-1 heading, landmarks, no FUDA) and drop the
placeholder string. Not urgent this milestone, but it is a scheduled break, not a
hypothetical one.

### L1 — role fixtures depend on `createUser`'s internal counter increment

`createAdmin` / `createPetugas` / `createSatgasPPKS` build their email from
`userIdCounter + 1` (`fixtures/user.ts:38,49,57`), pre-computing the value `createUser` is
about to increment to. It is correct today, and I found no collision, but the two must be
changed in lockstep. Have `createUser` accept a role-based email prefix instead of
predicting its own counter.
